# API Design

Design and scaffold REST APIs using FastAPI (Python) or Next.js API routes (TypeScript).

## Outputs
- `main.py` or `route.ts` — working API implementation
- OpenAPI schema (auto-generated by FastAPI, or manually defined)
- Example curl commands for every endpoint
- Dry-run test script (`test_api.sh` or inline GitHub Actions step)

## FastAPI conventions used in this project
```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Service Name")

class RequestModel(BaseModel):
    field: str

class ResponseModel(BaseModel):
    result: str

@app.post("/endpoint", response_model=ResponseModel)
async def endpoint(body: RequestModel) -> ResponseModel:
    ...
```

## Endpoint design rules
- Use nouns for resources: `/meetings`, `/employees`, `/artefacts`
- Use HTTP methods semantically: GET read, POST create, PATCH partial update, DELETE remove
- Return 422 for validation errors (FastAPI default), 404 for not found, 409 for conflicts
- Always include a `/health` endpoint returning `{"status": "ok"}`

## Dry-run test template
Before integrating with any external API, verify auth and reachability:
```bash
#!/bin/bash
set -e
BASE_URL="${API_BASE_URL:-https://api.example.com}"
TOKEN="${API_TOKEN:?API_TOKEN required}"

echo "Dry-run: testing $BASE_URL/health"
STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
  -H "Authorization: Bearer $TOKEN" \
  "$BASE_URL/health")

if [ "$STATUS" != "200" ]; then
  echo "FAIL: HTTP $STATUS"
  exit 1
fi
echo "PASS: API reachable and authenticated"
```

## Guidelines
- All endpoints must validate input via Pydantic/Zod — no raw dict parsing
- Document every endpoint with a one-line docstring (used by OpenAPI)
- Always call `store_result` with the implementation and example curl commands
